PROJECT: THE LAST BEACON — OFFLINE SURVIVAL COORDINATION SYSTEM

Act as a senior full-stack developer, UI/UX designer, and hackathon mentor. Build a complete, functional, responsive web application named THE LAST BEACON for a student hackathon. Do not merely create a design mockup. Implement the actual functionality, connect all interactions, test the application, and fix errors.

1. PROBLEM STATEMENT

It is Day 19 of a fictional zombie outbreak. Two friends, Aarav and Mira, are surviving in a city where communication networks have failed. They must reach a fortified survivor settlement called The Last Beacon.

Their challenges:

- No reliable internet or live navigation.
- Unknown routes and changing dangerous zones.
- Limited food, water, medicine, and battery.
- The need to coordinate their next moves.
- The risk of choosing a dangerous route or wasting essential supplies.

Build a survival-coordination prototype that helps them plan routes, monitor threats, conserve supplies, and make informed decisions without depending on live internet services.

This is a fictional simulation for a hackathon, not a real emergency-response or zombie-detection system.

2. TECHNOLOGY REQUIREMENTS

Use the existing supported project stack where possible.

Preferred stack:

- React
- TypeScript
- Vite
- Tailwind CSS if already available
- Lucide icons if available
- Browser localStorage for persistence
- SVG or CSS for a self-contained, interactive fictional city map

For Replit, create a runnable React application with the necessary package configuration and start command.

For Lovable, work within its existing project structure and dependencies.

Do not unnecessarily replace existing configuration files or install large dependencies. Avoid external map APIs, paid services, authentication, backend setup, and API keys. The application must be easy for beginner students to understand.

3. VISUAL DESIGN

Create a polished, cinematic, dark survival-command dashboard.

Design requirements:

- Dark charcoal and midnight backgrounds.
- Emerald green for safe zones and success.
- Amber for warnings.
- Red for danger and blocked roads.
- Blue or cyan for the selected route and navigation.
- Clear typography, consistent spacing, rounded panels, subtle borders, and accessible contrast.
- A professional emergency-operations dashboard aesthetic, not a generic business website.
- Responsive layouts for mobile phones, tablets, and laptops.
- No horizontal scrolling on a 360px-wide phone screen.
- Large touch-friendly buttons.
- Use functional icons, small status indicators, and simple transitions.
- Avoid excessive animations and heavy decorative imagery.

Create a sidebar on desktop and a compact navigation menu on mobile. The main dashboard should display the mission map, resource summary, current threats, and recommended action.

Application branding:
THE LAST BEACON
OFFLINE SURVIVAL COORDINATION SYSTEM
Tagline: “Plan smart. Adapt fast. Reach the beacon.”

Display a simulated Day 19 mission indicator and a clearly labeled offline/local-data status.

4. DASHBOARD AND NAVIGATION

Build the following functional sections, accessible through navigation or clearly organized panels:

A. Mission Overview
B. Interactive City Map
C. Route Planner
D. Supply Inventory
E. Threat Monitor
F. Survivor Coordination
G. Survival Advisor

The dashboard should provide a clear overview of the current route, supplies, threat level, survivor status, and next recommended action.

Do not create empty pages or buttons that do nothing. Every visible interactive control must have a meaningful behavior.

5. INTERACTIVE FICTIONAL CITY MAP

Build a self-contained city map using SVG, CSS, or a similarly lightweight local implementation.

Do not use a static screenshot as the map.

Create a fictional map with these locations:

- Safehouse: starting location for Aarav and Mira.
- Supply Depot: optional supply location.
- North Bridge: a road junction that may become dangerous.
- Old Hospital: a location with medicine supplies.
- Abandoned Market: a location with food and water.
- Safe Shelter: an intermediate safe location.
- The Last Beacon: final destination.

Connect the locations with roads. Give every road:

- A unique identifier.
- A starting node and ending node.
- A distance value.
- A danger score.
- A threat status.
- A blocked/unblocked status.

Display locations as clickable nodes and roads as visible connections. Use distinct visual states for safe, caution, dangerous, and blocked roads.

Show the starting location, final destination, available routes, and selected route. Provide a legend explaining map colors.

When a location is selected, display its name, status, and available information.

Make the map fit smaller screens without making the route unreadable.

6. FUNCTIONAL ROUTE-PLANNING ENGINE

Implement an actual graph-based route planner in JavaScript or TypeScript.

Use Dijkstra's algorithm or another understandable shortest-path algorithm.

Each road must have a travel distance and danger score. Calculate a route cost using a formula similar to:

routeCost = distance + dangerPenalty

Use a configurable danger multiplier. Dangerous roads must receive a significantly larger penalty than safe roads. Blocked roads must never be included in a valid route.

The route planner must:

- Find a route from Safehouse to The Last Beacon.
- Consider current road danger and blocked status.
- Select a valid, low-cost route.
- Show the selected route visually on the map.
- Display the route's estimated distance as simulated data.
- Explain why the route was selected.
- Recalculate when threats or road states change.
- Show an appropriate warning if no valid route exists.
- Never claim that simulated distance is real-world GPS distance.

Add a clearly visible “Recalculate Route” button.

Make route calculation a real function operating on the current road graph, not a hardcoded text change.

7. DYNAMIC THREAT SIMULATOR

Create a working Threat Monitor.

Include:

- “Update Threats” button.
- “Increase Danger” or equivalent controls for changing individual road conditions.
- Safe, caution, dangerous, and blocked states.
- A visible threat summary.
- A list of affected locations or roads.
- A timestamp or simulation turn number for the latest local update.
- A “Reset Scenario” button.

Threat updates must modify the underlying application state and immediately refresh the map, route, threat summary, and survival recommendations.

Create a deterministic demo scenario so judges can reproduce the same result during a presentation.

Provide an obvious demonstration button or preset that blocks or makes the current selected route dangerous and forces the planner to find another route.

If no alternative exists, clearly show that no valid route is available instead of inventing one.

Do not pretend the application detects real threats. All changes are simulated locally.

8. SUPPLY INVENTORY

Initialize the application with these demo values:

- Food: 6 units.
- Water: 4 units.
- Medicine: 2 units.
- Battery: 65%.

Display the four resources as attractive status cards with icons, quantities, and progress indicators where appropriate.

Implement working actions:

- Consume one food unit.
- Consume one water unit.
- Use one medicine unit.
- Use battery for a simulated device operation.
- Reset supplies through the overall reset function.

Requirements:

- Never allow a resource to fall below zero.
- Disable or handle actions when supplies are exhausted.
- Update the interface immediately after each action.
- Persist changes in localStorage.
- Display low-resource warnings.
- Ensure the advisor reads the current resource values.
- Do not let reset or refresh create inconsistent duplicate data.

Battery consumption should use a clear rule, such as reducing battery by 5 percentage points per simulated operation.

9. SURVIVOR COORDINATION

Create separate status cards for Aarav and Mira.

Display:

- Name.
- Current fictional location.
- Mission status.
- Next planned action.
- Resource or readiness indicator if appropriate.

Implement:

- “Confirm Plan” button.
- “Mark Ready” control for each survivor.
- Visible confirmed, pending, and ready states.
- A mission activity log showing recent local actions.

The confirmation controls must update shared state and remain consistent across the dashboard.

Clearly explain that these are simulated local states. Do not claim that changes synchronize between two separate phones because no multiplayer backend is being implemented.

10. RULE-BASED SURVIVAL ADVISOR

Create a working Survival Advisor that generates recommendations from current application state.

Use transparent, understandable JavaScript or TypeScript rules rather than a fake AI chatbot.

Example rules:

- If the selected route contains a dangerous road, recommend finding a safer route.
- If a road is blocked, recalculate the route.
- If water is low, recommend conserving water.
- If food is low, recommend checking available supply locations.
- If medicine reaches zero, show a resource warning.
- If battery is low, recommend reducing unnecessary device operations.
- If no valid route exists, clearly state that the route is unavailable and the scenario needs to be reconsidered.
- If a safe route is available and resources are adequate, summarize the next planned move.

Each recommendation must be derived from the current state and update when relevant state changes.

Display the reason for the recommendation, its severity, and a suggested next action.

Never show recommendations that contradict the actual selected route or current resource values.

11. LOCAL PERSISTENCE AND OFFLINE-FIRST BEHAVIOR

Use localStorage to save:

- Current supplies.
- Road danger and blocked states.
- Current selected route or route-related state where appropriate.
- Survivor readiness and plan confirmation.
- Mission activity log, if practical.

Requirements:

- Load saved state on application startup.
- Handle missing or invalid saved data safely.
- Keep all panels consistent with the same source of truth.
- Add a “Reset Demo” action that restores the original scenario and initial supplies.
- Avoid storing unnecessary information.

Do not use a network request for core route calculation, resource updates, threat simulation, or recommendations.

If time and the project setup permit, implement a proper service worker and caching configuration so the application can reopen after assets have been cached. Do not claim complete offline reopening unless it has actually been implemented and tested.

Clearly distinguish between local application functionality and real communication between devices.

13. DEMONSTRATION MODE

Create a reproducible demo workflow for hackathon judges.

Initial state:

- Aarav and Mira start at Safehouse.
- The Last Beacon is the destination.
- Food is 6, water is 4, medicine is 2, and battery is 65%.
- At least two possible routes exist.
- At least one route can become dangerous or blocked.
- At least one alternative route exists for the main demonstration.

Demo sequence:

1. Show the initial map and recommended route.
2. Show the resource inventory.
3. Trigger a threat update that makes the current route dangerous or blocked.
4. Recalculate the route and show the alternative, if one exists.
5. Consume a supply and demonstrate a changed inventory value.
6. Show the survival advisor responding to the updated threat and supplies.
7. Confirm the mission plan.
8. Refresh the application and demonstrate persistence.
9. Reset the demo to its original state.

Make this workflow reliable and easy to reproduce. Avoid random events that might cause the demonstration to fail.
